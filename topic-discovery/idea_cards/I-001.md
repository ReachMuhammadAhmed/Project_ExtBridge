ID:                     I-001       From problem(s): P-001
Title:                  Signal or noise? Which Linux kernel test robot performance-regression reports get acted on, and can report-time evidence rank them
Research question:      RQ1 (characterize) What share of the kernel test robot's performance-regression reports are acted on (fixed/reverted), disputed (noise, misattribution, expected trade-off) or ignored, and how has that changed 2016-2026?
                        RQ2 (explain) Which report-time evidence (effect size, reported %stddev, number of affected benchmarks/metrics, benchmark family, tested branch, whether functions changed by the blamed commit appear in the report's perf-profile deltas) distinguishes acted-on from other reports?
                        RQ3 (prioritize) Does an interpretable classical ranker over that evidence put acted-on reports ahead of others better than the robot's own order, an |%change| threshold, and a change/stddev rule, on a time-ordered split?
RQ form:                characterize + compare-explain + prioritize
Contribution type:      empirical study + dataset (with a predictive analysis)
Data source:            oe-lkp public-inbox archive (git clone https://lore.kernel.org/oe-lkp/git/0.git, opened 2026-11-04; 20,537 messages, 1,741 robot performance reports, 979 regressions); mainline kernel history (git.kernel.org / GitHub mirror) for fix/revert links
Data shape:             tabular-labelled (numeric fields parsed from reports) + short text (human replies, for labelling only)
Labels:                 acted-on = a mainline commit cites the report's Message-ID (Closes:/Link:) or reverts the blamed commit (73 of 979 so far, lower bound); disputed/accepted/ignored = manual coding of the 410 threads with human replies (about 1,061 replies), plus "no reply" (569)
AI method + reason:     labelled tabular features -> classical ML (logistic regression, gradient-boosted trees) with SHAP or coefficients for RQ2; small N and imbalance favour simple, interpretable models; no LLM needed
Baseline (current practice) + evidence link:
                        (a) robot's own report order and threshold (every report above its threshold is mailed: "kernel test robot noticed a 4.1% regression ..."); (b) rank by |%change|; (c) rank by %change / %stddev; (d) rule "perf-profile names a function the commit changed". Evidence of practice: LPC 2021 talk https://lpc.events/event/11/contributions/895/
Metric(s):              RQ1: proportions with 95% CIs, trend test; RQ2: odds ratios / Mann-Whitney effect sizes; RQ3: AUC-PR, precision@10/20 per month, recall of acted-on reports, time-split, compared with baselines by bootstrap CIs
Negative result would mean:
                        report-time evidence does not separate acted-on reports from the rest (ranker no better than |%change|): developers' choice depends on factors outside the report; still publishable as RQ1/RQ2 characterisation
Anti-generic tests:     engineer-substitution [pass: the engineer's rules are the baselines; RQ1/RQ2 produce knowledge no script gives] · LLM-swap [pass: no LLM] · baseline [pass: robot threshold/order]
Laptop feasibility guess (to be confirmed by the pilot):
                        yes: archive 709 MB, treeless kernel clone ~0.5 GB, parsing in minutes; manual coding of ~410 threads (~15-25 h); blamed-commit diffs fetched lazily (slow: minutes per commit over the network, so cache them)
